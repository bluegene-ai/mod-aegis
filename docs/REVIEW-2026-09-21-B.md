### 1.1 【新发现·中】SQL 字符串转义实现与自身注释方向相反

**位置**：`src/AcAegisPersistence.cpp:16-53`（`EscapeForCharacterDb`），消费点 `:248-249`（事件批量 INSERT）、
`:411-413`（offense upsert）。

代码注释（`:18-21`）声称：

> *"Doubling single quotes stays correct even when the server runs with `NO_BACKSLASH_ESCAPES`."*

**这句话反了。** 实际实现同时做了两件互相冲突的事：

```cpp
case '\'': result += "''";  break;   // 只对 NO_BACKSLASH_ESCAPES 成立
case '\\': result += "\\\\"; break;  // 只对默认模式成立
case '\n': result += "\\n";  break;  // 同上
```

两种 sql_mode 的实际语义：

| 输入字符 | 转义结果 | 默认模式写回 | `NO_BACKSLASH_ESCAPES` 写回 |
| --- | --- | --- | --- |
| `'` | `''` | `'` ✅ | **语法错误**（`''` 被解析为"空串结束+新串开始"） |
| `\` | `\\` | `\` ✅ | **两个 `\`** ❌ 数据被改 |
| `\n` | `\\n` | 换行 ✅ | **`\n` 两字符** ❌ 数据被改 |

也就是说：**要同时兼容两种模式，唯一正确的做法是"只把 `'` 加倍、`\` 保持原样"**——这能在
两种模式下都得到正确结果。当前实现"加倍 + 反斜杠转义"在默认模式下恰好正确（所以线上大概率
没暴露），在 `NO_BACKSLASH_ESCAPES` 下会**整批 INSERT 语法错误**，导致事件表静默丢记录、
offense 状态写不进去（处罚阶梯因此失忆）。

**风险敞口**：现有 `evidenceTag` / `detailText` 全部由固定标识符与 `std::to_string(数值)` 拼成
（如 `"SpeedEnvelope"`、`"observed=" + std::to_string(observed)`），因此**默认配置下不会触发**。
但这是一个"靠调用方不传反斜杠来保证正确"的隐式契约，`banReasonTemplate`（`:214`）等运维可配置
字符串一旦含 `\` 就会踩中。

**修复建议**（任选，推荐 1）：

1. **改用 prepared statement**：`CharacterDatabase.Execute(stmt)` 走异步池、参数绑定由驱动完成，
   彻底消除这一类问题。核心自己就是这么写的（`BanMgr.cpp:241-250` 用
   `CharacterDatabase.GetPreparedStatement` + `Execute`）。缺点是事件表是多行批量插入，
   需要一个 `CHAR_INS_...` 形式的 prepared statement（或退化为逐行 `Execute`，但会牺牲批量收益）。
2. 若坚持字符串拼接：**只对 `'` 加倍，删除 `\\`、`\n`、`\r`、`\Z` 四个 case**，并把注释改成
   "只做单引号加倍，因为它在默认模式与 `NO_BACKSLASH_ESCAPES` 下都正确"。

### 1.2 【新发现·中】地面高度缓存的默认参数使缓存几乎不命中，热路径 VMAP 开销仍近似 1 次/包

**位置**：`AcAegisMgr.cpp:1151-1196`（缓存逻辑）、`AcAegisConfig.h:42-43`（默认 `250` / `1.5f`），
唯一消费者 `AcAegisMgr.cpp:1700-1722`（`MaybeUpdateSafePosition`）。

命中条件（`:1158-1171`）：`nowMs - groundCacheMs <= 250ms` 且
`dx²+dy² <= 1.5²` 且 `|dz| <= 1.5`。

**问题**：缓存把"上一次查询点"记为基准，玩家在跑动时下一次采样已经离开基准点。
按 `MOVE_RUN = 7.0 yd/s` 计算，250ms 内位移 **1.75 码 > 1.5 码半径**，因此持续跑动时
**几乎每个包都 miss**。加上 `MaybeUpdateSafePosition` 在 `:1705` 会因
`FALLING/FLYING/ONTRANSPORT` 等标志直接早退（这些情况下不更新缓存），实际命中率更低。

**后果**：`MaybeUpdateSafePosition` 每包仍会触发一次
`Map::GetFullTerrainStatusForPosition`（`Map.cpp:1419`）——而该函数**无条件**执行静态 BIH
`GetAreaAndLiquidData` + 动态树 `GetAreaAndLiquidData`（`Map.cpp:1426-1427`）。这正是核心在
`Map.cpp:847-859` 专门写注释解释"必须惰性求值、不能在每个 spline 子步上跑"的那个查询。
100 个跑动玩家 × 10 包/秒 ≈ **1000 次 VMAP 双查询/秒**，全部落在 `MovementHandlerScript::OnPlayerMove`
的同步调用链里。

**修复建议**：把默认值调到能真正命中的量级，例如
`GroundCacheTtlMs = 300`、`GroundCacheRadius = 5.0`。注意**这不会削弱检测能力**：
- `DetectFly` 的高度判定用的是 `cur.z - groundZ`，地形在 5 码内变化通常远小于
  `flyMinHeightAboveGround = 6.0`；且 `DetectFly` 在 `:2606` 还会用
  `HasUnstableGroundReference(..., maxHorizontalDrift=2.0)` 交叉校验。
- `MaybeUpdateSafePosition` 只要求 `|sample.z - groundZ| <= 3.0`（`:1712`）作为"可安全回滚"的宽松条件。
- `DetectClimb` / `DetectWaterWalk` 各自还有独立的地面查询与几何交叉验证。

另外建议顺手评估：`SyncMovementBoundaryState`（`:927-981`）在**每个移动包**上做
4 次全量光环遍历（`IsServerAuthorizedAerialState`、`HasFallMitigationAura` 由
`BuildMovementContext` 走、`HasExternalMobilityAura`、`HasConfiguredAuraWhitelist` 内层 `HasAura`），
加上 `BuildMovementContext`（`:1198-1298`）自身的 4 次遍历，且 `SyncMovementBoundaryState` 在同一个包上
被调用了**两次**（`AnticheatUpdateMovementInfo` 一次、`OnPlayerMove` 一次，见 §2.2 的调用链）。
而核心已经提供了这些语义的 O(1) 版本：`Unit::HasHoverAura()`、`HasWaterWalkAura()`、
`HasGhostAura()`、`HasFlyAura()`、`HasIncreaseMountedFlightSpeedAura()`
（`Unit.h:1801-1833`，内部是 `m_modAuras[type].empty()` 的哈希查表，`Unit.cpp:5743-5746`）。
`HasFallMitigationAura` / `IsServerAuthorizedAerialState` / `HasExternalMobilityAura` 目前是
**手写 `GetAppliedAuras()` 遍历**，完全可以先用上述 O(1) 谓词做前置短路，只在为真时才遍历取 caster。

### 1.3 【中】`DeletePlayerData` / `PurgeAllData` 的 `Barrier()` 会阻塞 world 线程

**位置**：`AcAegisPersistence.cpp:111-129`（`Barrier`）、`:462-485`（消费点）。

`Barrier()` 在 world 线程上 `_condition.wait(...)` 等待后台 worker 把删除边界之前的批次
交给异步池。若 DB 抖动或事件积压（队列上限 4096），这个等待时间无上界，world 线程会**同步停等**。
触发条件是 GM 手动执行 `.aegis delete` / `.aegis purge`（`AcAegisScripts.cpp:267`、`:274`），
不是热路径，所以危害有限；但与"把写库挪出热路径"的初衷相冲突。

**修复建议**：给 `Barrier()` 加超时（例如 2 秒），超时后继续删除并写一条警告审计；
或把 delete/purge 也投递到一个一次性后台任务里，GM 命令立即返回。

### 2.1 【严重·仍未解决】风险闸门在数学上使处罚阶梯不可达，`OffenseTierFloor` 只治标

**参数**（`AcAegisConfig.h` + conf 默认值）：`MaxDeltaPerMove = 30`、`HalfLifeSeconds = 75`；
阈值 `Notify 60 / Rollback 110 / Debuff 150 / Jail 210 / Kick 260 / Ban 320`。

**机制**：`DetectXxx` 产出的 `riskDelta` 一律经 `ClampRiskDelta`（`AcAegisMgr.cpp:64-67`）
截到 **≤30**；`HandleEvidence`（`:3767-3768`）先 `DecayRisk` 再累加。
稳态风险按 `R = 30 / (1 − 0.5^(T/75))` 计算（T = 同类证据间隔秒）：

| 证据间隔 T | 稳态风险 R | 可达档位 |
| --- | --- | --- |
| 11 s | 320 | Ban |
| 13 s | 284 | Kick |
| 17 s | 237 | Jail |
| 24 s | 165 | Debuff |
| 44 s | 110 | Rollback |
| 75 s | 60 | Notify |
| **> 75 s** | < 60 | **连 GM 通知都不会产生** |

即：**证据间隔超过约 24 秒的作弊者永远进不了 Debuff；超过 75 秒连通知都没有。**

`OffenseTierFloor`（`:3450-3456`）新增了
`stageByRisk = max(stageByRisk, StageFromTier(ctx.punish.offenseTier))`，但它的前提是
`ctx.punish.offenseTier > 0`，而 `offenseTier` 只在 `finalStage != Observe` 时增长
（`ShouldCountOffenseForPunishStage`，`:263-267`，配合 `offenseCountOnlyOnPunish = true`）。
于是形成**自举死锁**：

```
tier = 0
  → floor 不生效
  → 只有 risk ≥ 150 (Debuff) 才会让 tier 变成 1
  → 而 risk ≥ 150 要求证据间隔 ≤ 24 s
  → 间隔 > 24 s 的作弊者 tier 永远是 0，floor 永远不生效
```

**结论**：`OffenseTierFloor` 只对"已经被罚过一次"的玩家起保级作用（防止降档），
对**首次**因间歇性作弊而被处罚**毫无帮助**。这与 `docs/DESIGN.md` §6「Repeat Offense Rules」和
需求第 2 条直接冲突。默认参数下整条阶梯在实践中退化为
**"Observe + 偶发 Rollback/Notify"，Debuff 以上基本不会触发**。

**修复建议**（建议 1+3 组合）：

1. **给强证据 + 高危类型一条不依赖当前 risk 的地板**。`BasePunishStage`（`:651-693`）已经把
   `CoordinateTeleport` / `StationaryCoordinateShift` / `LowGravityJump` / `SuperJumpApex(Strong)`
   直接映射到 `Jail`，这些类型每条证据都是"物理上不可能"的事件，用"事件频率"来累加风险本身就是
   错误的模型。建议：对 `BasePunishStage >= Jail` 的证据直接以 `baseStage` 为下限，
   `ApplyRiskGate` 只用于**没有**强证据的情形。
2. **让 offense tier 直接参与判罚而非仅参与档位**：例如 tier ≥ 2 时，
   `evidence.level == Strong` 即允许 Jail，不再要求当前 risk。
3. **重标定阈值/衰减配比**：把 `Risk.HalfLifeSeconds` 提到 300 s 量级，或把
   `MaxDeltaPerMove` 与阈值按 1:5 重新配比，使"每分钟一次强证据"能到达 Jail 档。
   这需要实机回归（"事件频率 → 处罚档位"）后确定，conf 里应把这条量化关系写清楚。
4. 至少在 conf 注释中明确写出：**闸门本质是"持续事件频率门槛"，把阈值调低并不能覆盖间歇性作弊**。

### 2.2 【严重·新发现】`OnUnderAckMount` 被核心 28 处调用，且模块无条件清空全部检测状态

**位置**：`AcAegisMgr.cpp:4545-4586`（尤其 `:4585 ResetMovementDetectionState(ctx);`）。

模块注释（`:4555-4560`）自述该 Hook 只对应两类事件：上马/坐骑速度光环、服务端强制位移。
**但核心实际有 28 个调用点**（已全部枚举追踪），远不止这两类：

| 类别 | 核心调用点（节选） |
| --- | --- |
| 上马/下马 | `Unit.cpp:10226`（`Unit::Mount`）、`:10318`（`Unit::Dismount`） |
| **任意速度光环重算** | `SpellAuraEffects.cpp:3831`（`HandleAuraModIncreaseSpeed`）、`:3876`（`HandleAuraModIncreaseFlightSpeed`） |
| 水上行走/缓落/漂浮光环 | `SpellAuraEffects.cpp:3464`、`:3486`、`:3512` |
| 假死 | `SpellAuraEffects.cpp:2948` |
| 载具进出 | `Unit.cpp:15174`、`:15216`、`:15288`、`:15368` |
| 解除魅惑 | `Unit.cpp:14481` |
| 离开传送带 | `MovementHandler.cpp:480` |
| 速度变更 ACK | `MovementHandler.cpp:746` |
| 强制位移 | `SpellEffects.cpp:1154,1197,1221,1265,5197,5226,5301,5324,5423` |

**关键放大点**：`AuraEffect::HandleEffect` 的注册表把 **`SPELL_AURA_MOD_INCREASE_SPEED`(31)、
`MOD_INCREASE_MOUNTED_SPEED`(32)、`MOD_SPEED_ALWAYS`(129)、`MOD_MOUNTED_SPEED_ALWAYS`(130)、
`MOD_SPEED_NOT_STACK`(171)、`MOD_MOUNTED_SPEED_NOT_STACK`(172)、`MOD_MINIMUM_SPEED`(305)** 全部
指向 `HandleAuraModIncreaseSpeed` → 该函数在 `mode & AURA_EFFECT_HANDLE_CHANGE_AMOUNT_MASK`
时**无条件**调用 `AnticheatSetUnderACKmount`（`SpellAuraEffects.cpp:3829-3832`）；
`HandleAuraModIncreaseFlightSpeed` 更是对 6 种飞行速度光环（206–211）生效
（`SpellAuraEffects.cpp:3840-3877`，`:3874-3877` 的调用**不在任何 mode 判断内**）。

也就是说：**任何一次速度类光环的 amount 变化或重应用**（圣骑士十字军光环随坐骑/天赋重算、
竞速/迅捷/加速类 buff 叠层、飞行坐骑速度光环刷新……）都会调用模块的 `OnUnderAckMount`。

**后果（漏报方向）**：`:4585` 无条件执行 `ResetMovementDetectionState`，它会
- `ctx.samples.Clear()`（`:855`）→ 所有要求 `samples.Size() >= 2` 的检测器当拍失效；
- 清零 `speedHits` / `noClipBlockedHits` / `teleportBurstHits` / `stationaryMoveHits` /
  `climbHitsInWindow` / `superJumpHitsInWindow` / `flySuspicionHits` / `airStallHits` /
  `waterWalkHits` / `forceMoveHits` / `doubleJumpHits`（`:856-882`）。

于是**只要速度光环在反复重算，速度/传送/穿墙/飞行/爬墙的"窗口内累计命中"判据就永远无法成立**。
配合 `looksLikeMount` 为真时设置的 `lastMountAckMs`（`:4566`），还会让
`recentMountGrace`（`forceMoveGraceMs` 之外的 `mountGraceMs = 2500`）在 `shouldSkipAllDetectors`
（`:1272`）里持续生效，形成**接近全检测免检**的窗口。

注意这与已修好的 `SyncMovementBoundaryState`（`:927-981`）形成**内部不一致**：后者只在
"边界真的发生变化"时才 `ResetMovementDetectionState`（`:949-961`），是正确写法；而
`OnUnderAckMount` 是同一模块里的无条件版本。

**修复建议**（拆成两件事）：

1. **把重置改为条件式**。只在"确实发生了边界变化"时重置，与 `SyncMovementBoundaryState` 对齐：
   ```cpp
   bool wasMounted = ctx.observedVehicleState;  // 或单独的 observedMounted 标志
   bool isMountedNow = looksLikeMount;
   if (isMountedNow != wasMountedNow) { ctx.lastMountAckMs = _elapsedMs; ResetMovementDetectionState(ctx); }
   ```
2. **不要用"是否上马"来区分两类事件**。`looksLikeMount`（`:4561-4563`）在"骑乘状态下的击退/拉拽"
   场景下必然为真，会把服务端强制位移误判成上马，从而**不设置 `lastServerForceMoveMs`**
   （走 `:4566` 分支），使 `recentServerForceMoveGrace` 失效。更可靠的做法是区分**触发来源**，
   例如让脚本层注册不同的 hook，或至少用"`ctx.lastMountAckMs` 是否在极近的过去"+
   "位移量是否已发生"做交叉判断。

> 实机验证建议：给一个骑乘角色挂一个会周期性重算的速度光环（或反复上下坐骑速度光环），
> 同时制造小位移，观察 `ac_aegis_event` 是否**完全没有** `SpeedEnvelope` / `BlockedSegment` 记录。
> 若确认，本条升级为"严重"。

### 2.3 【中·仍未解决】Pull 家族（`IgnoredPull`）依然不可达

`HasControlledPullEffect`（`AcAegisMgr.cpp:714-720`）在 `OnSpellCast`（`:4444-4448`）里
只设置 `ctx.lastControlledPullMs` 与 `lastSpellGraceMs`，**从不调用 `ArmControlledMoveExpectation`**。
`AegisControlledMoveKind::Pull` 唯一出现处是 `ControlledMoveTag`（`:730-731`）。
因此 `DetectControlledMove` 永远不会产出 `IgnoredPull`。

需要澄清的是：**这本身不是"拉拽类外挂漏报"**。`lastControlledPullMs` 会进入
`recentControlledPullGrace`（`:1248`），而后者在 `shouldSkipAllDetectors`（`:1278`）里，
所以拉拽**期间**的位移被豁免；拉拽结束后靠 `DetectTeleport` / `DetectSpeed` 兜底。
真正的问题是：**"反拉拽/抗位移"这一类作弊（客户端拒绝服务端下发的位移）完全没有检测**——
模块本来打算用 `IgnoredPull` 覆盖它（`DetectForceMove` 是对击退的同类实现，见 `:1433-1486`）。

**修复建议**：不要硬塞进 `OnPlayerSpellCast`（该 Hook 是施法侧，拿不到目标侧的最终位移）。
可行路径：
- 在 `Spell::EffectPullTowards` / `EffectKnockBack` 的调用点（`SpellEffects.cpp:5301`、`:5423`）
  已经在打 `AnticheatSetUnderACKmount`；若核心侧愿意加一个带 `(target, kind, expectedDistance2D, expectedDeltaZ)`
  参数的新 Hook，模块就能对 Pull 建立与击退同级的期望窗口。
- 在模块内不改核心的替代方案：不再依赖 Hook，改为在 `OnUnderAckMount` 命中**且**该玩家
  在极短时间内出现在"被拉拽"位置附近时 arm 期望——但这不如核心侧 Hook 干净。
- 若短期不做，**应把 `AegisControlledMoveKind::Pull`、`ControlledMoveTag` 的 `IgnoredPull` 分支、
  以及 conf 中相关注释一并删掉**，避免留下假的扩展点（上一轮的 `OnJumpOpcode` 就是同类问题）。

### 2.4 【中】`OnJumpOpcode` 的 `jump == true` 分支仍是死代码（但语义侥幸成立）

`AcAegisScripts.cpp:370-373` 接的是 `AnticheatSetJumpingbyOpcode`。已证实核心对该 Hook 只有
**两个调用点**，且**都硬编码传 `false`**（`MovementHandler.cpp:637`、`:647`），全仓库无一处传 `true`。
所以 `OnJumpOpcode` 的 `if (!player || !jump) return;`（`:4615`）永远命中，
`ctx.lastJumpOpcodeMs` **不会**由这个 Hook 赋值。

它实际由 `HandleDoubleJump`（`:4802`、`:4809`、`:4819`、`:4844`、`:4880`）赋值，
而 `AnticheatHandleDoubleJump` 只在 `MSG_MOVE_JUMP` 上被调用（`MovementHandler.cpp:564-572`），
且**早于** `AnticheatCheckMovementInfo`。所以 `recentJump` / `recentExtendedJump`
（`AcAegisMgr.cpp:1256-1257`）的语义侥幸仍然正确——但这是一条**隐式跨 Hook 副作用依赖**，
任何"打开 `PLAYERHOOK_ANTICHEAT_SET_JUMPING_BY_OPCODE`"的人都会合理地以为它有效。

**修复建议**：二选一——(a) 从 `AcAegisPlayerScript` 的 Hook 列表里摘掉
`PLAYERHOOK_ANTICHEAT_SET_JUMPING_BY_OPCODE` 并删除 `OnJumpOpcode`，在 `HandleDoubleJump` 顶部
用注释说明"跳跃时间戳只在这里设置"；(b) 保留但在 `OnJumpOpcode` 顶部注释清楚"核心只传 false"。

### 2.5 【低-中】`OnPlayerMove` 未按 opcode 过滤，其中 `CMSG_MOVE_FALL_RESET` 语义可疑

已证实 `OnPlayerMove`（`MovementHandler.cpp:660`）位于 `ProcessMovementInfo` 内部，
因此它会被 **47 个 opcode** 触发，其中包括纯 ACK 与状态变更包：
`CMSG_MOVE_KNOCK_BACK_ACK`、`CMSG_FORCE_MOVE_ROOT_ACK`、`CMSG_FORCE_MOVE_UNROOT_ACK`、
`CMSG_MOVE_HOVER_ACK`、`CMSG_MOVE_FEATHER_FALL_ACK`、`CMSG_MOVE_WATER_WALK_ACK`、
`CMSG_MOVE_SET_CAN_FLY_ACK`、`CMSG_MOVE_GRAVITY_*_ACK`、`CMSG_DISMISS_CONTROLLED_VEHICLE`、
以及 10 个速度变更 ACK。模块的 `OnPlayerMove`（`:4636-4682`）**完全不看 `opcode`**，
所有包都会走 `CaptureSample` + 全部检测器。

其中 `CMSG_MOVE_FALL_RESET`（`HandleMovementOpcodes` 在 `:407-408` 于 `ProcessMovementInfo`
**之后**才 return）尤其需要实机确认：该包在 3.3.5a 里被客户端用于重置坠落状态，
其坐标/时间字段的语义与其他移动包不一致。若该包的 `movementInfo.pos` 是"上一位置"，
则会产生一次虚假的大位移，可能命中 `DetectTeleport`（阈值 18 码）。

**修复建议**：在 `OnPlayerMove` 顶部排除 ACK 类 opcode（至少
`CMSG_MOVE_FALL_RESET`、`CMSG_MOVE_CHNG_TRANSPORT`、各 `*_ACK`），或至少对它们
只做 `SyncMovementBoundaryState` 不做检测。

### 2.6 【低】`DetectMount` 在允许坐骑的地图上只能记录、无法处罚

`:2907-2912` 在 `!indoors && allowMount` 时直接早退；`:2920-2921` 在
`indoors && allowMount` 时要求 `mountIndoorMinMoveDistance`。因此
`DisallowedMapMount`（`!allowMount`，risk 14）是唯一能在非副本场景稳定产出的分支，
而它要过 `risk >= 150` 的闸门（见 §2.1）。结合 §2.1，**坐骑类检测在实践中只能写日志**。
这属于取舍，但 conf 与 README 应明确写出该上限。

### 2.7 【低】`DetectTime` 只覆盖明显的时间超前

`:1403` 要求 `ratio >= 1.35` 且 `leadMs >= 180`。1.1–1.2 倍的"温和时间倍率"无覆盖。
建议写进 conf 的上限说明，避免运维误以为已覆盖全部时间作弊。

## 3. 不误报

整体方向正确：单次证据只能触发回滚/通知，处罚同时受风险闸门、`banStrongEvidenceRequired`
与 `banMinOffenseCount` 约束；`BasePunishStage` 决定地板不决定天花板。以下是可以收紧的缺口。

### 3.1 【中·新发现】受控位移宽限只覆盖一半路径，击退/拉拽后的真实位移可能被判为瞬移

**位置**：`AcAegisMgr.cpp:4545-4586`（宽限设置）、`:1263-1264`（消费）、
`MovementHandler.cpp:824-853`（`HandleMoveKnockBackAck`）、`SpellEffects.cpp:5261-5263`。

核心的击退速度公式是 `speedxy = MiscValue * 0.1`，`speedz = damage * 0.1`
（`SpellEffects.cpp:5261-5263`）。典型 `MiscValue = 200` → `speedxy = 20 yd/s`；
`damage = 30` → `speedz = 3`，滞空时间约 0.6 s。大击退（`MiscValue = 400`）则接近 **1.2 s**，
正好等于 `forceMoveGraceMs = 1200`（`AcAegisConfig.h:120`）——**余量为零**。

时序上：服务端在 `EffectKnockBack` 里打 `AnticheatSetUnderACKmount`
（`SpellEffects.cpp:5301`）→ 设置 `lastServerForceMoveMs`，宽限 1200 ms 内
`shouldSkipAllDetectors` 为真。但客户端是在**飞完之后**才发 `CMSG_MOVE_KNOCK_BACK_ACK`
（`HandleMoveKnockBackAck`，经 `ProcessMovementInfo` 进入 `OnPlayerMove`）。若飞行时间 + 网络延迟
超过 1200 ms，落地后的**下一个普通移动包**（`movementInfo.pos` 已在落点、无 `FALLING` 标志）
就会被当作"凭空位移"进入 `DetectTeleport`：
- `axisDelta >= 25` 或 `dist >= 45` 时直接判 `CoordinateTeleport`（`:2332-2333`）→ `shouldRollback = true`
  （`:2384`）→ 玩家被**回滚到击退前的位置**；
- 否则按 `TeleportBurst`，需要 1800 ms 内 2 次（`:2339-2349`）。

`DetectForceMove`（`:1444`）只处理 `cur.opcode == CMSG_MOVE_KNOCK_BACK_ACK` 且"移动太少"的情形，
`DetectTeleport` 在 `:2278` 只跳过带 `ONTRANSPORT/SWIMMING/FALLING/FALLING_FAR` 的**当前**包，
对"落地后的第一个包"没有保护。

**修复建议**：

1. **把击退宽限从"ACK 包"绑定改为"服务端确实下发过位移 + 期望位移量"**。核心已经在
   `EffectKnockBack` 里知道 `speedxy`/`speedz`/方向，模块可通过现有 Hook 之外的信号获取；
   短期可用的近似是：在 `OnUnderAckMount` 命中"强制位移"分支时，把宽限从
   `forceMoveGraceMs` 提升到一个能覆盖实际飞行时间的值（例如按 `jump.zspeed` 估算，
   或在 conf 里给出 `ForceMove.GraceMs` 的建议下限 2500），并同时在
   `DetectTeleport` 里增加"当前包坐标与 `lastServerForceMoveMs` 时刻的预期落点接近"的豁免。
2. **给 `DetectTeleport` 增加 opcode 白名单/黑名单**（见 §2.5），至少让落地后的第一包不因
   "与上一包距离大"被判瞬移——因为这种情况在正常游戏中必然出现（击退/传送/载具/复活）。
3. 在 `purge`/`release`/`jail` 等自身传送之后，模块已经能通过 `OnBeforeTeleport`
   （`:4484-4487`）设置宽限；但核心内部的 `NearTeleportTo` **不经过该 Hook**
   （已在 `Player.cpp:1498` 证实只有 `Player::TeleportTo` 调用它），见 §3.2。

| **`NearTeleportTo` 且不经 `Spell::EffectTeleportUnits` 的脚本/核心调用** | ❌ **无任何宽限** | 无 Hook |
| **同级地图 `Player::TeleportTo`** | ❌ **无宽限** | `TeleportTo` 的同图分支不调 `OnPlayerMapChanged`，`OnMapChanged` 只在 `Map::AddPlayerToMap`（`Map.cpp:285`）触发 |

**后果**：上述场景之后玩家的下一个移动包会报告一个新位置。若位移落在
`axisDelta >= 25` 或 `dist >= 45`，会命中 `CoordinateTeleport`（Strong + rollback）——
**玩家被从战场出生点/boss 传送落点拉回原处**。这是明确的功能性误报。

**修复建议**（模块内可做，不需要改核心）：

1. 在 `OnPlayerMove` 中增加一层"服务端位移自检"兜底：当本包位移超阈值、但
   `cur.z` 与 `GetGroundHeight` 的差值合理、且**上一步安全点与新位置之间的几何可达性成立**
   时，降级为 `Medium` 且不 rollback（区分"被服务端搬过去"与"客户端瞬移"本身很难，
   但"不 rollback"能消除最有害的副作用）。
2. 更实用的是**用核心已有的信号做豁免**：`Player::IsBeingTeleported()` 在 `TeleportTo`
   的 near/far 语义期间为真（`Player.h:2121`），而 `HandleMovementOpcodes` 在
   `:373-377` 会据此直接跳过 `ProcessMovementInfo`（因此 `OnPlayerMove` 不会被调用）。
   问题在于 **`NearTeleportTo` 不设该信号**。建议在模块里检测
   "`player->GetPositionX()` 与本包 `movementInfo.pos` 相同但上一采样点相距很远"
   —— 即位置已被服务端改写过 —— 并据此重置采样链而不产出证据。
   实现上可在 `CaptureSample` 前比较 `ctx.samples.Newest()` 与 `player->GetPositionX()`
   （服务端权威位置），二者不一致说明服务端刚搬过玩家。
3. 在 README/conf 中明确记录"核心与脚本的 `NearTeleportTo` 不会通知 Aegis"这一已知边界，
   供运维判断误报来源。

### 3.3 【低-中·仍未解决】`DetectAfk` 对"站桩采集"仍会命中

条件（`AcAegisMgr.cpp:3076-3113` + `TouchGatherWindow:2132-2177`）：
窗口 ≥ `afkWindowMs = 600000`（10 分钟）、动作 ≥ 12、拾取 ≥ 4 或采集 ≥ 6、
窗口起点位移 ≤ `afkMaxMoveDistance = 6` 码、动作间隔 ≥ 1.5 s、检测时不在战斗且存活。

一个**手动**玩家在同一个采集点反复采药/挖矿（密集刷新点）10 分钟、位移 < 6 码、
采集 ≥ 6 次，会完全满足条件并产出 `GatherLoop`。`afkMinLootCount = 4` 对"反复开同一个箱子/
矿点"同样成立。战斗重置（`:2145-2149`）只在"拾取/采集的那一刻处于战斗"才生效，
很多采集点的怪物在采集时并不处于战斗中。

减轻项：`DetectAfk` 的处罚被 `afkMinSuspiciousWindows = 2` 压制
（`DetermineAction:3432-3437` 把首个窗口的档位压到 Debuff），所以首次命中不会直接监禁。
但 `stage1DebuffSeconds = 86400`（24 小时的 debuff）作用在误判玩家身上仍然非常难受。

**修复建议**：
1. 把"窗口内是否击杀过敌对目标 / 是否发生过战斗"与"零位移"**同时**作为处罚前置
   （目前是"检测时不在战斗"，太弱）。
2. 强档位（`afkStrongActions = 20`）与 `moved <= afkStrongMoveDistance` 应作为
   **处罚**的硬前置，弱档位只写日志。
3. 默认把 `afkEnabled` 设为 0，或在 conf 顶部明确"开启前必须先观察一周日志"。

### 3.4 【低】`.aegis clear` 的权限分层已修好，但 `banMode` 语义需要写清

已核实：核心**根本没有** ban mode 概念——`account_banned`/`character_banned` 表没有 mode 列
（`LoginDatabase.cpp:76`、`CharacterDatabase.cpp:36`），`BanMgr` 也不存/不解析 mode
（`Misc/BanMgr.h:37-45`）。模块的 `lastBanMode` 是**模块自有字段**，用于决定解除时调哪个
`RemoveBan*`。`ClearCoreBanState`（`AcAegisMgr.cpp:3338-3388`）在 mode 未知时拒绝执行并告警
（`:3376-3385`），这是正确的保守做法。

需要提醒运维的一点：**默认 `banMode = "account-by-character"` 是唯一"真正封得住"的模式**。
核心的 `BanCharacter`（`BanMgr.cpp:224-269`）只写 `character_banned` 表、**不阻止登录**；
只有 `BanAccount` / `BanAccountByPlayerName` 会写 `account_banned`（登录时检查）。
若运维把 `AcAegis.AutoAction.Ban.Mode` 改成 `character`，封禁将退化为"仅标记角色"。
当前默认值正确，建议在 conf 该键旁加一句明确警告。

### 3.5 【低】`purge` / `clear` 的释放传送与监狱拦截的顺序已修好

`:4045-4056`（purge）与 `:3955-3974`（clear）都先清内存 punish 状态再传送，因此
`OnBeforeTeleport`（`:4464-4466`）不会再拦掉自己的释放传送。上一轮 §3.2 已修好。

### 3.6 【低】`DetectClimb` 的 `SteepClimb` 分支在几何未阻挡时仍会产出证据

`:3041-3051`：`geometry.CheckShortSegment` 未阻挡时，只有
`(cur.z - curGroundZ) > flyMinHeightAboveGround` 或 `(prev.z - prevGroundZ) > ...` 才 return；
否则继续产出 `SteepClimb`。判据为 `slopeRatio >= 1.73`（约 60°）。
正常游戏中"贴着墙根跳/挤"可能短时满足，但最终档位受 `climbHitsInWindow >= 3`
与风险闸门约束，风险可接受。建议在实机回归里专门观察楼梯/Boss 台阶场景。
